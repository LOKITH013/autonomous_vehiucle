======================================================================
1. PROJECT PURPOSE
======================================================================

Astra ADAS is a research prototype for video-based road-scene perception
and driver-assistance telemetry, with emphasis on Indian Driving
Conditions (IDD). It combines object detection, tracking, lane and traffic
heuristics, approximate distance and motion estimates, time-to-collision
(TTC), rule-based risk levels, and recommendation labels.

The application does not control a vehicle. Its distance and TTC values
are not calibrated measurements, and its recommendations are not validated
driving commands. Do not use the prototype as a real-world safety system.

3. PROCESSING ARCHITECTURE
======================================================================

Offline video processing flow:

Video frame
  -> YOLO object detection and ByteTrack association
  -> classical OpenCV lane detection
  -> traffic-light/sign detection post-processing
  -> optional MiDaS relative-depth estimate
  -> fallback bounding-box distance proxy when depth is unavailable
  -> per-track relative motion estimate
  -> TTC calculation
  -> geometric in-path hazard check
  -> rule-based risk assessment
  -> rule-based recommendation
  -> annotated frame and per-object CSV record

The dashboard's Live Camera path is a separate, smaller flow:

Browser camera frame
  -> existing YOLO detector and tracker
  -> bounding boxes, class/confidence labels, and class summary
  -> annotated frame returned to the browser over WebRTC

5. MODULE GUIDE
======================================================================

src/perception/detector.py
   Loads the YOLO checkpoint, filters relevant classes, runs detection and
   ByteTrack, and returns class, confidence, bounding box, and track ID.

src/tracking/tracker.py
   Contains a DeepSortTracker placeholder. The active application path uses
   YOLO's ByteTrack integration instead.

src/lane/lane_detector.py
   Uses grayscale conversion, blur, Canny edges, a trapezoid region of
   interest, and probabilistic Hough lines. Estimates lane position and
   lateral deviation, smooths brief gaps, and draws lane overlays.

src/traffic/traffic_detector.py
   Uses YOLO traffic-light and traffic-sign boxes. It classifies light color
   from the box crop with HSV thresholds as RED, YELLOW, GREEN, or UNKNOWN.
   Signs are counted but their types are not classified.

src/hazard/hazard_detector.py
   Checks whether an object's bottom-center footprint falls between detected
   lane boundaries. If lane lines are unavailable, it uses a configurable
   central image corridor.

src/depth/depth_estimator.py
   Optionally runs MiDaS Small to produce a relative inverse-depth map. A
   configured scale factor converts this into a rough distance estimate;
   this scale is not camera-calibrated.

src/motion/motion.py
   Provides a bounding-box pinhole distance proxy and per-track motion
   estimates. It reports closing-speed proxy and image-plane direction
   (left/right/up/down); these are not world-coordinate measurements.

src/ttc/ttc_calc.py
   Computes TTC as distance divided by closing speed when there is enough
   history and closing speed exceeds the configured minimum. Otherwise TTC
   is missing or infinite.

src/risk/risk_engine.py
   Produces LOW, MEDIUM, or HIGH risk with explanatory reason strings using
   configured TTC/distance cutoffs, traffic-light state, lane context, and
   in-path status.

src/decision/decision_engine.py
   Produces STOP, AVOID OBSTACLE, BRAKE, SLOW DOWN, MONITOR, or
   MAINTAIN SPEED and returns reasons. These are prototype recommendations.

src/pipeline/pipeline.py
   Integrates the detectors and decision modules for video, draws output,
   reports processing progress, and writes per-object metrics.

src/dashboard/app.py
   Primary Streamlit UI for project video, uploads, Live Camera, sidebar
   detection classes, benchmark metrics, and system modules.

src/dashboard/api.py
   FastAPI endpoints for health, video listing/serving, uploads, background
   pipeline jobs, status checks, result downloads, and live-frame detection.

src/dashboard/live_camera.py
   Draws live-camera object boxes, labels, confidence, and a class summary
   onto each webcam frame.

web/src/App.jsx
   React dashboard interface for video analysis, job status, results,
   webcam capture, and detections.

web/src/styles.css
   Responsive dashboard theme and layouts.

web/vite.config.js
   Vite development server configuration and local API proxy.

src/evaluation/benchmark_m4.py
   Compares the COCO-pretrained baseline with the IDD checkpoint using
   per-class AP@50, mAP@50, precision/recall/F1 at an operating threshold,
   latency, and throughput. It can write charts and a report.

src/evaluation/evaluate.py
   Reads pipeline metrics CSV and creates risk/action/class charts and an
   experimental summary report.

scripts/inspect_idd.py
   Inspects raw IDD files for image/annotation counts, matching filenames,
   duplicate samples, unreadable images, and sample annotation structure.

scripts/train_improved.py
   Training entry point for the planned YOLOv8s IDD-D training run. The
   script defaults to 50 epochs and 960-pixel input and accepts training
   arguments such as batch size, workers, device, and dataset YAML path.

scripts/astra_m5_colab_training.ipynb
scripts/astra_m5_kaggle_training.ipynb
   Notebook alternatives for GPU-hosted training.

   High-risk distance cutoff: 5.0 meters (proxy)
   Medium-risk distance cutoff: 12.0 meters (proxy)

Decision:
   Brake TTC cutoff: 1.5 seconds
   Slow-down TTC cutoff: 3.0 seconds

All of these are prototype parameters, not universal safety thresholds.
config.manual.yaml changes the pipeline output paths for manual testing.

Rule order used by the current decision engine:
   1. A RED traffic-light state returns STOP.
   2. An obstacle classified in the path returns AVOID OBSTACLE.
   3. TTC below 1.5 seconds returns BRAKE.
   4. TTC below 3.0 seconds returns SLOW DOWN.
   5. Otherwise, HIGH risk returns SLOW DOWN and MEDIUM risk returns
      MONITOR.
   6. If none of those conditions apply, the result is MAINTAIN SPEED.

Risk is evaluated separately: a RED light immediately produces HIGH risk;
in-path TTC below 2.0 seconds is HIGH, below 4.0 seconds is MEDIUM; and an
in-path distance proxy below 5.0 or 12.0 meters produces HIGH or MEDIUM
risk respectively. A vulnerable road user at MEDIUM risk is promoted to
HIGH. The decision engine's ordering means an in-path obstacle label can
take precedence over the TTC action. These are code rules, not validated
operational advice.

13. WHAT THE MEASURED METRICS MEAN
======================================================================

The detector benchmark uses labeled IDD-D images and compares predicted
boxes to ground-truth boxes:

AP@50:
   Area under the precision-recall curve for one class, matching a
   prediction to a ground-truth box at Intersection-over-Union (IoU) >=
   0.50. It summarizes detector ranking across confidence values.

mAP@50:
   Mean of the AP@50 values for classes that have ground-truth objects in
   that split. This is a detection metric, not a measure of safe driving.

Precision:
   At the selected operating confidence threshold, the fraction of
   predictions that match a labeled object. Higher precision means fewer
   false positive detections.

Recall:
   At the selected operating confidence threshold, the fraction of labeled
   objects that the detector found. Low recall means missed objects.

F1:
   Harmonic mean of precision and recall at the operating threshold.

IoU:
   Intersection area divided by union area for predicted and labeled boxes.
   The benchmark treats a match as correct at IoU >= 0.50.

Latency and FPS:
   Mean detector inference time per image and corresponding throughput.
   These figures do not include the full lane/depth/risk dashboard pipeline,
   browser transport, or camera permission/startup time.

16. HOW THE IMPLEMENTED SYSTEM HELPS
======================================================================

Research and development:
   The project turns a video into visible, inspectable intermediate outputs:
   detected classes and boxes, track IDs, lane estimates, light-color
   estimates, risk levels, action labels, and reason strings. This makes it
   easier to inspect model behavior frame by frame and identify cases that
   need better data, calibration, or logic.

Indian road-scene coverage:
   The IDD class list explicitly includes autorickshaws, riders, animals,
   and vehicle-fallback objects in addition to cars, buses, people, and
   other common classes. The test benchmark shows a higher aggregate
   mAP@50 for the IDD checkpoint than the COCO baseline on the reported
   IDD-D split. This supports further research on domain-specific
   perception, while low-recall classes remain visible areas for improvement.

Contextual prioritization:
   Tracking links detections across adjacent frames. Lane geometry and the
   central-corridor fallback help identify objects that may occupy the
   projected path, rather than treating every visible object equally.
   TTC and rule-based risk/action labels provide a consistent way to
   organize candidate events for review.

Explainability:
   Risk and decision functions return reason text such as threshold
   crossings or an obstacle-in-path condition. Researchers can inspect why
   a label was produced instead of seeing only an unexplained score.

Operator visualization:
   The dashboard lets a user test existing clips, upload a clip, or point
   the browser at a laptop webcam. The live view is useful for a local
   demonstration of the detector and for observing its class labels and
   confidence values; it is not a validated on-road deployment.

Reproducible experiments:
   Per-frame/per-object CSV files and annotated videos preserve pipeline
   outputs for later analysis. The M4 evaluator compares detector
   checkpoints and inference resolutions, while the M15 evaluator summarizes
   risk/action/class distributions. This helps track changes between
   model/configuration runs and identify where further tests are needed.

Dataset and training workflow:
   The dataset inspector helps discover missing image/annotation pairs,
   duplicate samples, unreadable files, and annotation formats before
   conversion or training. The training scripts/notebooks provide a path
   toward completing the planned GPU training milestone.

These are development and research benefits. No measured result in this
document demonstrates reduced collisions, safe driving, calibrated
distances, or validated real-time performance in a vehicle.

20. FUTURE SCOPE AND RECOMMENDED ORDER
======================================================================

Priority 1 - Complete and validate the model training:
   Run the planned YOLOv8s IDD-D training on a GPU using
   scripts/train_improved.py or one of the Colab/Kaggle notebooks. Compare
   checkpoints on validation data, choose a model, and then run the
   full held-out test benchmark. Keep the test split out of training and
   model selection.

Priority 2 - Run the full ADAS pipeline on live camera frames:
   Add lane detection, traffic-light/sign processing, hazard checks, motion,
   TTC, risk, and decision telemetry to the webcam callback. Add a way to
   save a webcam session as an annotated video and CSV, with explicit start,
   stop, and error state handling.

Priority 3 - Calibrate metric estimates:
   Calibrate the camera and distance geometry or use suitable metric-depth
   ground truth. Rework and validate the distance proxy/MiDaS scale, then
   measure closing-speed and TTC error against labeled scenarios before
   presenting those values as physical measurements.

Priority 4 - Improve and validate road understanding:
   Evaluate lane position and lane boundaries against labeled images.
   Validate traffic-light color under day/night/rain/occlusion and associate
   signals with the ego lane. Add a labeled dataset/model if traffic-sign
   subtype recognition or hazards such as debris and potholes are required.

Priority 5 - Build scenario-level evaluation:
   Test across multiple videos and varied roads, weather, lighting, and
   traffic density. Report per-class detection metrics and suitable tracking
   metrics such as MOTA/IDF1. Validate risk and decision labels against
   ground-truth events, and report false positives and missed hazards.

Priority 6 - Improve live runtime and operator feedback:
   Measure end-to-end webcam FPS/latency on target hardware, expose stream
   errors and inference status, and verify browser permissions and camera
   behavior across supported browsers. Provide an operator feedback/event
   review workflow only if those records can be stored and evaluated safely.

Priority 7 - Add other input sources:
   Consider recorded camera devices, RTSP/network streams, or CARLA only
   after the local webcam path and source lifecycle are reliable.

All future work remains research/prototype work until validated. The system
must not be connected to vehicle controls or described as safety-certified
without the required engineering, ground-truth validation, and review.

21. USE CASES
======================================================================

Use case 1 - Demonstrate road-user detection:
   Select Live Camera, allow browser camera permission, and show how the
   configured IDD detector labels visible road users such as cars, buses,
   people, riders, or autorickshaws. Use this as a local visual demo of
   object detection only; the webcam path does not currently run the full
   ADAS logic.

Use case 2 - Review a recorded road video:
   Select a project MP4 or upload a road clip. Run the offline pipeline to
   inspect object tracks, lane estimates, traffic-light/sign telemetry,
   in-path labels, approximate TTC/risk, and recommendation reasons frame
   by frame. Use the annotated MP4 to review scenes and the CSV to filter
   individual object records.

Use case 3 - Compare detection checkpoints:
   Run the M4 benchmark against labeled IDD-D validation/test images to
   compare AP/mAP, precision, recall, F1, latency, and throughput. Use
   validation results for model selection and reserve the test split for
   final evaluation.

Use case 4 - Compare inference resolutions:
   Use the 640-pixel and 960-pixel benchmark configurations to examine the
   trade-off between detector accuracy and latency on the same sampled
   validation subset. Do not equate detector FPS with end-to-end video or
   webcam FPS.

Use case 5 - Inspect dataset readiness:
   Run scripts/inspect_idd.py against the raw dataset to identify missing
   image/annotation pairs, duplicate samples, unreadable images, and
   annotation formats before converting data or starting training.

Use case 6 - Explore prototype risk outputs:
   Review logged risk levels, action labels, and reason strings to identify
   scenes for follow-up analysis. Confirm these outputs against labeled
   ground truth; do not treat them as proven warnings or driving advice.

22. CONCLUSION
======================================================================

Astra ADAS currently provides an end-to-end research workflow: it can
process recorded road video, run configured IDD object detection and
tracking, combine detections with lane/traffic/hazard heuristics, estimate
relative motion and TTC, produce explainable rule-based risk/action labels,
and export annotated video and CSV records. The primary Streamlit dashboard
supports existing videos and uploads, and its Live Camera option provides
a browser-based object-detection demonstration.

The measured IDD checkpoint has higher reported detection mAP@50 than the
COCO baseline on the saved IDD-D test report (0.371 versus 0.127). The
640/960 validation experiment also shows an accuracy/latency trade-off.
These results support continued domain-specific research; they do not
validate the full ADAS pipeline, metric distance/TTC, real-time end-to-end
performance, or safety.

The next major steps are to complete the planned GPU training run, validate
the selected checkpoint, calibrate and measure distance/TTC, improve and
validate lane/traffic understanding, run labeled scenario-level tests,
and then extend the live-camera path to the full pipeline with appropriate
logging. Until those steps are complete, use the project for development,
demonstration, and offline research analysis only.
